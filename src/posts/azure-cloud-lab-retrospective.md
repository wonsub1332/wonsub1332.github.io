# Azure 클라우드 실습 회고 - 인프라 엔지니어의 첫 걸음

## 들어가며

약 한 달 동안 Azure를 활용한 클라우드 인프라 실습을 진행했다.

처음에는 Azure Portal 화면만 봐도 조금 막막했다. 메뉴도 많고, 서비스 이름도 익숙하지 않아서 어디서부터 봐야 할지 잘 감이 오지 않았다. 그런데 Virtual Network부터 Load Balancer, NAT Gateway, Azure SQL Database까지 하나씩 직접 만져보면서, 클라우드 환경에서 서비스가 어떤 식으로 구성되는지 조금씩 눈에 들어오기 시작했다.

이번 글에서는 실습 과정에서 배운 내용을 너무 딱딱하지 않게, 실제로 내가 이해하게 된 흐름 중심으로 정리해 보려고 한다.

---

## 1. Azure의 시작

Azure는 Microsoft에서 제공하는 클라우드 플랫폼이다.

예전에는 클라우드라고 하면 그냥 "가상 서버를 만드는 곳" 정도로만 생각했는데, 이번 실습을 하면서 생각보다 훨씬 넓은 영역을 다룬다는 걸 느꼈다. 서버를 띄우는 것만이 아니라 네트워크를 나누고, 보안을 설정하고, 트래픽을 분산하고, 데이터베이스와 모니터링까지 연결하는 과정 전체가 하나의 흐름으로 이어져 있었다.

특히 아래 같은 장점들은 실습하면서 꽤 인상적으로 다가왔다.

- 빠른 인프라 구축
- 사용량 기반 과금
- 높은 가용성
- 다양한 관리형 서비스 제공
- 글로벌 리전 지원

이번 실습에서는 Azure Portal을 이용해 리소스를 직접 만들고 연결해 보면서, 각각의 서비스가 어떤 역할을 하는지 조금씩 몸으로 익혀갈 수 있었다.

---

## 2. Virtual Network(VNet)와 Subnet

Azure를 보면서 가장 먼저 익숙해져야 했던 개념은 Virtual Network(VNet)이었다.

처음에는 이름이 조금 거창하게 느껴졌지만, 결국 클라우드 안에서 사용하는 사설 네트워크라고 생각하니 이해가 쉬웠다. 이번 실습에서도 VM만 띄우는 데서 끝나는 게 아니라, 네트워크를 나눠서 웹 서버와 애플리케이션 서버의 역할을 분리하는 방식으로 구성했다.

```text
VNet: 10.0.0.0/16
|- Web Subnet: 10.0.1.0/24
`- WAS Subnet: 10.0.2.0/24
```

직접 나눠서 구성해 보니 웹 서버와 애플리케이션 서버의 역할이 훨씬 또렷하게 보였다. 왜 실무에서 계층별로 네트워크를 분리하는지, 책으로 읽을 때보다 훨씬 더 쉽게 이해됐다.

---

## 3. NSG(Network Security Group)

NSG는 Azure에서 방화벽처럼 동작하는 보안 설정이라고 이해하면 편했다.

실습에서는 각 서버 역할에 맞춰 필요한 포트만 열어두는 방식으로 규칙을 구성했다.

### Web 서버

허용:

- HTTP (80)
- HTTPS (443)
- SSH (22)

### WAS 서버

허용:

- Tomcat (8080)
- SSH (22)

차단:

- 외부 인터넷에서의 직접 접근

이걸 직접 설정해 보니 "일단 다 열어두고 나중에 막는 것"보다, 처음부터 필요한 것만 허용하는 게 왜 중요한지 확실히 와닿았다. 서버가 통신만 되면 끝나는 게 아니라, 어떤 접근을 허용할지 정하는 것 자체가 인프라 설계라는 생각이 들었다.

---

## 4. NAT Gateway

Private Subnet에 있는 VM은 Public IP가 없기 때문에 인터넷에 직접 연결할 수 없다.

처음에는 "외부에서 못 들어오면 더 안전한 것 아닌가?" 정도로만 생각했는데, 막상 운영 관점에서 보면 서버도 바깥으로 나가야 할 일이 꽤 많았다. 운영체제 업데이트를 하거나, 패키지를 설치하거나, 외부 API를 호출해야 하는 경우가 그렇다. 이런 상황을 해결해 주는 게 NAT Gateway였다.

구성 후에는 Private VM에서도 다음과 같은 작업이 가능해졌다.

- `apt update`
- 패키지 다운로드
- 외부 API 호출

반면 외부에서는 여전히 Private VM으로 직접 접근할 수 없었다.

이걸 구성하고 나니 Private VM을 외부에 노출하지 않으면서도 필요한 작업은 할 수 있다는 점이 꽤 인상적이었다. 보안과 운영 편의성 사이에서 균형을 맞추는 방식이 이런 거구나 싶었다.

---

## 5. Azure Bastion

처음에는 원격 접속을 하려면 당연히 Public IP가 있어야 한다고 생각했다.

그런데 Azure Bastion을 사용하면 Public IP 없이도 브라우저를 통해 SSH나 RDP 접속이 가능했다. 직접 써보니, 서버를 운영할 때 서비스용 접근 경로와 관리용 접근 경로를 분리해서 생각하는 게 중요하다는 걸 알 수 있었다.

Azure Bastion의 장점은 다음과 같았다.

- 관리용 포트 미노출
- 보안성 향상
- VPN 없이 원격 접속 가능

실제로 사용해 보니 모든 서버에 Public IP를 붙이지 않아도 충분히 관리가 가능했다. "관리하려면 일단 외부에 열어야 한다"는 생각에서 조금 벗어나게 해준 구성요소였다.

---

## 6. Azure Load Balancer

서비스가 서버 한 대에서만 동작하면 그 서버에 문제가 생겼을 때 전체 서비스가 영향을 받게 된다.

그래서 실습에서는 Load Balancer를 두고 여러 서버로 요청을 분산하는 구조를 만들어 봤다.

```text
Internet
  |
Public Load Balancer
  |
+-----+-----+
|           |
Web1       Web2
```

Load Balancer는 사용자의 요청을 여러 서버에 분산시켜 주며, 이를 통해 다음과 같은 효과를 기대할 수 있다.

- 부하 분산
- 고가용성
- 장애 대응

예전에는 그냥 요청을 나눠주는 장치 정도로 생각했는데, 직접 구성해 보니 서비스의 안정성과 가용성을 받쳐주는 중요한 축이라는 느낌이 들었다.

---

## 7. Apache Reverse Proxy와 WAS 분리

이번 실습에서 개인적으로 가장 재미있었던 부분 중 하나는 Web 서버와 WAS 서버를 나눠서 구성해 본 것이었다.

Web 서버에는 Apache를 설치하고, WAS 서버에는 Tomcat을 설치해서 각자 맡는 역할을 분리했다.

구조는 다음과 같았다.

```text
User
  |
Apache (Web)
  |
/api
  |
Internal Load Balancer
  |
Tomcat WAS
```

Apache는 정적 콘텐츠를 처리하고, API 요청만 WAS 서버로 넘기도록 설정했다.

평소에는 Web-WAS 분리라는 말을 자주 들어도 조금 추상적으로 느껴졌는데, 직접 구성해 보니 왜 이런 구조를 쓰는지 훨씬 쉽게 이해됐다. 서버마다 맡는 일이 분명해지니까 전체 구조도 더 깔끔하게 보였다.

---

## 8. Azure SQL Database

이번에는 데이터베이스 서버를 직접 설치하는 대신 Azure SQL Database를 사용해 봤다.

처음에는 직접 설치해서 운영하는 방식이 더 익숙하게 느껴졌지만, 관리형 서비스를 써보니 왜 많은 환경에서 이런 방식을 선호하는지 조금 알 것 같았다.

대표적으로 다음과 같은 점이 인상적이었다.

- 자동 백업
- 자동 패치
- 고가용성 제공
- 간편한 확장

특히 백업이나 패치 같은 운영 부담을 많이 덜 수 있다는 점이 크게 느껴졌다. 인프라 엔지니어 입장에서 "직접 다 해야 한다"보다 "안정적으로 맡길 수 있다"는 선택지가 있다는 게 꽤 현실적으로 다가왔다.

---

## 9. Azure Monitor

실습을 하면서 느낀 건, 인프라는 구축만 잘한다고 끝나는 게 아니라는 점이었다.

실제로 서비스가 돌아가기 시작하면 그다음부터는 상태를 계속 확인할 수 있어야 하고, 문제가 생겼을 때 빨리 알아차릴 수 있어야 한다. 그런 면에서 Azure Monitor는 운영 단계에서 꼭 필요한 도구처럼 느껴졌다.

Azure Monitor를 활용하면 다음과 같은 정보를 수집하고 확인할 수 있다.

- CPU 사용률
- 메모리 사용량
- 네트워크 트래픽
- 로그

이 부분을 보면서 서버를 만드는 것만큼, 그 서버를 계속 지켜보고 관리하는 일도 중요하다는 걸 다시 느꼈다. 결국 인프라는 "띄우는 것"보다 "안정적으로 운영하는 것"까지 포함해서 봐야 한다는 생각이 들었다.

---

## 최종 아키텍처

실습을 마치고 나서 가장 크게 남은 건, Azure의 각 서비스가 따로 노는 게 아니라 하나의 구조 안에서 자연스럽게 이어진다는 점이었다.

전체 흐름을 정리하면 다음과 같다.

```text
Internet
  |
Public Load Balancer
  |
+-------------------+
|                   |
Web1 (Apache)   Web2 (Apache)
  \               /
   \---- /api ----/
          |
Internal Load Balancer
          |
+-------------------+
|                   |
WAS1 (Tomcat)   WAS2 (Tomcat)
          |
Azure SQL Database
```

처음에는 각각의 서비스가 전부 따로 보였는데, 실습을 계속하다 보니 네트워크, 보안, 로드밸런싱, 애플리케이션 분리, 데이터베이스, 모니터링이 전부 하나의 흐름 안에서 연결된다는 점이 조금씩 보이기 시작했다.

---

## 마치며

이번 Azure 실습은 단순히 VM 몇 대를 만들어 보는 경험이라기보다, 하나의 서비스 구조를 클라우드 위에서 어떻게 조립해 나가는지 직접 따라가 본 시간에 가까웠다.

특히 VNet, NSG, NAT Gateway, Bastion, Load Balancer, Reverse Proxy 같은 개념들은 글로만 볼 때보다 직접 연결해 봤을 때 훨씬 더 잘 이해됐다. 각각은 따로 배운 것 같았지만, 결국 하나의 아키텍처 안에서 다 이어져 있었다.

아직 부족한 점은 많지만, 직접 구성해 보면서 클라우드를 보는 눈이 조금은 넓어진 느낌이 들었다. 앞으로는 Azure에만 머물지 않고 AWS에서도 비슷한 구조를 다시 만들어 보면서, 클라우드 아키텍처에 대한 이해를 더 깊게 쌓아가고 싶다.
